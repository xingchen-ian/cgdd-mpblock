多人游戏，从一句话开始

每台电脑各跑一份完整的游戏，中间连一根只传“变化”的管子。

两个世界

单机：状态只有一份，你按下按键，屏幕就变。

联机：状态有 N 份。A 把门打开了，B 的机器什么都不知道——除非有人专门告诉它。

所以联机开发只做两件事：传什么，和听谁的。

四个问题

一份游戏变成 N 份，就会冒出四个问题。

① 传什么，怎么传？
世界不能整个传，只能传变化		② 冲突时听谁的？
两份副本不一致，总得有一边说了算
③ 这是状态还是事件？
晚进来的人看不到事件		④ 我怎么知道我是对的？
网络不可见，只能自己造证据

一局三分钟的合作游戏

四个问题，同一局里都会出现。

  1. 两人一起拉杆开门。A 拉了杆，B 那边门没动。→ ①
  2. 两人同时踩同一块板，各说各的“我先踩的”。→ ②
  3. 第三个人中途进来，看见门是关的——可门明明开过。→ ③
  4. 打到一半，两边分数不一样了，但各自看起来都正常。→ ④

管子到底是什么

IP 找到机器，端口找到程序。 默认端口 7777。

一个包几十到几百字节，每个包都可能丢。

场景往返延迟
同机 127.0.0.1< 1 ms
教室有线 / WiFi1–3 ms / 5–30 ms
互联网30–150 ms
你看到的永远是几十毫秒之前的世界。

什么是 UDP，为什么是 UDP

TCP 为了“顺序”会等你；位置信息等不起。

TCPUDP
保证送达是否
保证顺序是否
丢一个包后面全部排队（队头阻塞）丢就丢了，下一个覆盖它
游戏里用来需要可靠的东西位置、朝向
需要可靠的地方（“我捡到旗子了”）在 UDP 上自己补一层——这就是 Unity Transport 做的。

传的是变化，不是一个世界

左边一大坨，几兆；右边一个信封，几十字节。

整个世界这一帧动了什么
场景 + 所有物体 + 所有属性7 号对象，位置 +0.3，朝向 12°

只传三种东西：登记过的字段 · 变了的字段 · 压缩过的值。

设计时盯着的不是“场景长什么样”，是“什么在变”。

按拍子发 · 插值 · 不做什么

发送频率约 30 次/秒（tick），不是每帧。

插值默认开着，学生什么都不用设。 两次采样之间做平滑，代价是：你看到的别人比真实时间还晚 33–66 ms。

要瞬移，不要关插值——在权威端调用 SyncedTransform.Teleport(pos, rot, scale)， 接收方这一帧会重置插值，不会出现“滑过整张地图”。

我们故意不做为什么
客户端预测 / 服务器回滚要确定性模拟和逐帧历史
延迟补偿要重放过去的输入
不做意味着：玩法要避开需要“精确到毫秒判定”的设计。

谁是谁

服务器得说得出“7 号”，客户端还得认得出它。

对象身份从哪来学生要做什么
玩家NetConfig.playerPrefab 上的 NetworkObject用生成器就不用管
运行时生成（子弹、箱子）登记进 NetConfig.spawnablePrefabs必须手动加，忘了就生成失败
场景里摆的（门、方块）生成器自动加 NetworkObject自己新建的物体要自己加
NetworkObject 必须在根物体上；模型只是挂在下面的“一层皮”。

谁说了算

客户端权威 Owner服务器权威 Server
适合自己的位置、自己的动画分数、血量、门、胜负
手感立即、顺滑要等一个往返
风险想改就能改规则复杂，要写验证

值积木没有选项：SyncedBool / SyncedInt / SyncedFloat 永远归服务器， 客户端只能 RequestSet。

三段式：客户端发请求 → 服务器验证 → 服务器广播结果。

这是状态，还是事件？

状态 State事件 Event
现在为真的值此刻发生的事
门开着 · 比分 3:2 · 血量 40拉了一下杆 · 开了一枪 · 回合开始
会持续，直到有人改它发生完就过去了
晚加入的人：会收到当前值晚加入的人：收不到
SyncedBool / Int / FloatNetEvent
事件的效果如果必须留下，它就不是事件，是状态。

三个判断练习

下面六个，哪个是状态，哪个是事件？

  1. 门是否打开
  2. 拉了一下杆
  3. 当前比分
  4. 开了一枪
  5. 我在哪一队
  6. 回合开始
陷阱题：“我捡到了旗子” —— 两个都要：事件说明发生过，状态说明现在在谁手上。

三个最常见的错

  1. gameId 两边不一致 → SESSION_ID_MISMATCH，看起来连上了却进不去
  2. spawnablePrefabs 忘了登记 → 运行时生成失败
  3. 改的是场景里的副本，不是这个 .asset → 改完没生效
同一个场景 + 不同 NetConfig = 不同的游戏。
