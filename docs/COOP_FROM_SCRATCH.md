# Build the co-op door from scratch

This is the hand-built version of the co-op mission: every object, every component, every
reference. Nothing is generated for you except the empty scene itself.

`MPBlocks > Add Co-op Door Kit to Scene` does all of this in one click. **Do not use it for the
exercise** — build it by hand once, then compare with the kit if something does not work.

---

## 0. What you are building

Two levers, one door, one rule:

> Both levers must be pulled **within 2.5 seconds of each other**. Pull one, walk to the other
> too slowly, and the first lever springs back.

That rule is what makes it a two-player puzzle instead of a solo button press.

---

## 1. Scene skeleton

Create an empty scene (`File > New Scene > Empty`), then add four objects:

| Object | Components | Why |
|---|---|---|
| `NetworkManager` | `NetworkManager`, `UnityTransport` | the networking core |
| `Net` | `NetBootstrap` | starts host/client, owns the config |
| `SessionCanvas` | see below | the Host/Join screen |
| `Ground` | `Cube` scaled `(20, 0.5, 20)` at `(0, -0.25, 0)` | something to stand on |

Then create the config: `Assets > Create > MPBlocks > Net Config`, name it `NetConfig_CoopDoor`,
and drag it into `Net > NetBootstrap > Config`.

Fill the config:

| Field | Value |
|---|---|
| Port | 7777 |
| Max Players | 4 |
| Game Id | `coop-door` (must match on every machine or the client is rejected) |
| Player Prefab | `Assets/Prefabs/Player.prefab` |
| Player Movement | `Transform` |

**Session panel shortcut:** select `SessionCanvas` in `Assets/Scenes/Bootstrap.unity`, copy it,
paste it into your scene. It is a pile of uGUI objects — rebuilding it by hand teaches nothing
about networking, and `NetSessionUI` finds the `NetBootstrap` on its own.

Finally: `NetworkManager` → `Network Settings`:
- `Player Prefab` → `Assets/Prefabs/Player.prefab`
- `Network Transport` → the `UnityTransport` on the same object

## 2. Lever A

Create an empty object `Lever_A` at `(2.6, 0, 0)`. Add four components, in this order:

| Component | Field | Value | Why |
|---|---|---|---|
| `NetworkObject` | — | — | every networked object needs one |
| `Interactable` | Label | `LeverA` | shown in `[MP]` logs |
| | Max Distance | `4` | server re-checks this against the player's position |
| `SyncedBool` | Label | `LeverAOn` | replicated on/off state |
| `InteractToggle` | Interactable | drag `Interactable` | who toggles it |
| | State | drag `SyncedBool` | what to toggle |
| | Target Renderer | the handle (below) | what to recolour |
| | Off / On Colour | grey / orange | visual feedback |

Now the handle: add a child `Cube` named `Handle` at `(0, 1, 0)`, scale `(0.25, 1, 0.25)`,
colour whatever you like. Drag its `MeshRenderer` into `InteractToggle > Target Renderer`.

Now the audio twin of the colour change: add **`Interact Sound`** to `Lever_A`, drag
`Assets/Audio/Interact_Approved.asset` into **Approved Clip** and `Interact_Denied.asset` into
**Denied Clip** (both are generated by the toolkit; replace them with your own clips any time —
the clip lives on the object, so each lever can sound different).

| Field | Value | Why |
|---|---|---|
| Approved / Denied Clip | the two clips | played when the server approves / refuses |
| Volume | `0.8` | |
| Spatial Blend | `0.7` | 3D so distant levers are quieter |
| Local Player Only | off | on = only the player who pressed E hears it |

**No collider is needed.** `PlayerInteractor` finds the nearest `Interactable` by distance; it
does not raycast.

## 3. Lever B

Duplicate `Lever_A` (`Ctrl/Cmd + D`), rename to `Lever_B`, move to `(-2.6, 0, 0)`.
Make sure the copies still point at their **own** components, not A's.

## 4. The door

Create an empty object `Door` at `(0, 0, 6)`:

| Component | Field | Value |
|---|---|---|
| `NetworkObject` | — | — |
| `SyncedBool` | Label | `DoorOpen` |

Child: a `Cube` named `DoorPanel` at local position `(0, 1.6, 0)`, scale `(3.2, 3.2, 0.3)`.

The door's closed position is captured from the panel's **local** position when the object
spawns, so the panel must be a **child** of `Door`.

Now add `CoopDoor` on `Door`:

| Field | Value | Why |
|---|---|---|
| Is Open | `SyncedBool` (`DoorOpen`) | the state late joiners replay |
| Levers | `Lever_A`'s `Interactable`, `Lever_B`'s `Interactable` | the server listens to their `Approved` events |
| Door Panel | `DoorPanel` transform | what slides |
| Open Offset | `(0, 3.4, 0)` | local metres the panel moves |
| Required Levers | `2` | how many must fire |
| **Window Seconds** | **`2.5`** | all levers must fire inside this window |
| Reset Levers On Timeout | ✅ | lets the levers visibly spring back |
| Slide Seconds | `0.6` | panel animation, local only |

---

## 5. Spawn points

Four empty objects named `SpawnPoint_1` … `SpawnPoint_4`, spread apart (e.g. `(3,0,0)`,
`(0,0,3)`, `(-3,0,0)`, `(0,0,-3)`), each with a `PlayerSpawnPoint` component.

The server sorts them by name and hands them out round-robin. Without them everyone spawns on
the origin, inside each other.

---

## 6. Build settings

`File > Build Settings > Add Open Scenes`. Only needed for player builds; Play mode works
without it.

## 7. Test

1. Play, press **Host**.
2. Join from a second player (a build, or `./tools/run-local.sh 2`).
3. One player pulls a lever, then walks slowly to the other one.

| What you should see | Meaning |
|---|---|
| `DOOR_PROGRESS pulled=1 required=2` | the first lever counted |
| `DOOR_ATTEMPT_RESET reason=window_expired lost=1 window=2.5` | the rule worked: too slow |
| the lever turns grey again | `Reset Levers On Timeout` |
| two players pull within 2.5 s → `DOOR_OPENING`, `DOOR_OPENED` | success |

---

## 8. Tune the rule

| Field | Effect |
|---|---|
| `Window Seconds = 1.5` | brutal: they must stand ready |
| `Window Seconds = 3–4` | forgiving |
| `Window Seconds = 0` | old behaviour — one player can do it alone |
| `Required Levers = 3` | a three-player gate (add a third lever) |
| `Reset Levers On Timeout = off` | levers stay on, but the progress still resets |

---

## 9. If it does not work

| Symptom | Cause |
|---|---|
| nothing happens on E | no `PlayerInteractor` on the player prefab, or the lever is further than `PlayerInteractor.range` (3.5 m) |
| `INTERACT_DENIED reason=out-of-range` | server-side `Interactable.maxDistance` is smaller than you think |
| the lever recolours but the door never moves | `CoopDoor.Levers` does not reference the lever's `Interactable` |
| the door opens on the first lever | `Required Levers` is 1 |
| the door never opens | `Required Levers` is larger than the `Levers` array length |
| the door moves the wrong way | `Open Offset` is in the door's **local** space |
| every client sees the door shut while the host sees it open | the panel is not a child of `Door`, or `Is Open` is not wired |
| a late joiner sees a closed door | `Is Open` was never wired to the `SyncedBool` |
